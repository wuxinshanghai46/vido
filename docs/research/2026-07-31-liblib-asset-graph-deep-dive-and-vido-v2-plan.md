# Liblib 资产图深拆与 VIDO 精细化方案 V2

> 日期：2026-07-31
> 结论性质：产品与技术方案，不是已实现功能
> 本文修正上一版“8 类业务节点 + 资产卡片”的粒度不足问题，优先解决“第二阶段必须真正产出人物与场景资产”，再讨论高级画布。

## 一、修正后的核心结论

可以为每个剧情广告任务自动形成类似竞品的关联画布，但画布不应成为普通用户的默认工作流。

VIDO 应采用三层结构：

1. **普通用户层**：参考与目标、资产准备、故事与镜头、生成与审核四个工作区。
2. **资产生产层**：人物、产品、场景、道具均有候选、锁定版本、质量状态和下游引用。
3. **生产血缘层**：系统根据真实任务、资产版本和生成记录自动投影成关系图，仅对超管和获授权人员开放。

正确的建设顺序是：

1. 先把第二阶段做成真正可产出、筛选和锁定人物/场景资产的工作台。
2. 再让故事板和镜头明确消费已锁定资产。
3. 最后把已经存在的生产关系自动投影成高级画布。

如果先做画布、后补资产能力，只会得到一张看起来专业、实际没有稳定输入的流程图。

## 二、本轮从竞品界面确认的事实

### 2.1 保时捷 718 案例

只读查看的项目：

- 18 个可见分组。
- 93 个媒体节点，其中 64 个图片节点、29 个视频节点。
- 119 条显式连线。
- 除媒体生成外，还存在裁剪、旋转与镜像等中间资产处理。

这说明竞品的精细化不在“步骤数量”，而在同一个任务中保留了大量可复用的中间资产和依赖关系。

### 2.2 人物资产不是一张人物图

人物主资产分组中可见 10 个节点，包含：

- 全身人物概念图。
- 正面、侧面、背面的全身三视图。
- 独立脸部三视图。
- 服装、头盔/面部遮挡、局部特征等补充参考。
- 多套人物版本或候选。

已直接读取到的节点配置包括：

- 人物全身母版：先生成欧洲女性赛车手、黑色赛车服、手持头盔的全身概念。
- 人物三视图：基于选中的人物图，生成正面、侧面和背面，黑色背景，并保留 2 个候选。
- 人物入景关键帧：用人物三视图驱动悬崖/森林环境中的半身镜头，并保留 4 个候选。
- 关键帧再连接到一个或多个视频节点。

所以人物正确的数据流不是：

```text
人物描述 → 故事板
```

而是：

```text
人物方向
  → 人物概念候选
  → 身份主版本
  → 脸部三视图
  → 全身三视图
  → 服装与遮挡补充
  → 人物连续性包锁定
  → 人物入景关键帧候选
  → 视频镜头
```

### 2.3 场景不是一句环境提示词

在一个明确的场景分支中，界面同时连接了：

- 外部上传的环境氛围图。
- 单独裁剪出的跑车产品图。
- 三个不同镜位/构图的场景关键帧候选。
- 一个继续消费关键帧的视频节点。

其中一个低机位森林公路镜头显式引用了产品图片，提示中还包含机位、动态模糊、车辆清晰区域、时间、色调、景深、广告质感和画幅要求。

因此场景正确的数据流是：

```text
空间定义
  → 场景氛围母版
  → 空间布局与光线锁定
  → 按镜头需求生成主视图/反打/交互位
  → 人物或产品入景关键帧候选
  → 视频镜头
```

场景母版与“人物/产品已经进入场景后的镜头关键帧”必须分开，不能混成一个 `SceneAsset`。

### 2.4 故事板是策划视图，不是完整生产图

竞品故事板使用左右两栏：

- 左侧是被选用的图片资产。
- 右侧是被选用的视频资产。
- 卡片显示名称、候选数、分辨率或时长。
- 本案例故事板当前可见 6 个图片项和 6 个视频项，并没有把 93 个底层媒体节点全部展示给用户。

这证明“生产图”和“用户故事板”应该是两个投影：

- 生产图回答：从哪里来、依赖谁、重做会影响什么。
- 故事板回答：最终选择了哪些画面，按什么叙事顺序组成作品。

### 2.5 竞品画布也会失控，不能照搬

另一个人物型案例中：

- 89 个可见节点。
- 88 个是视频节点。
- 只有 7 条显式连线。
- 没有分组。

这更像生成历史堆积，而不是严谨的生产血缘。

VIDO 应借鉴“资产可追踪、版本可回退、镜头显式引用”，不应借鉴“所有生成结果都平铺到无限画布”。

## 三、第二阶段必须改成“资产准备工作台”

上一版把人物、产品、场景放在资产卡片中，但没有定义资产如何真正生成、如何验收、何时才能进入下一阶段。V2 将第二阶段定义为可执行的资产生产流程。

## 3.1 第二阶段的入口

第一阶段完成后，系统只产出一份轻量的“创作蓝图”：

- 广告主体与不可变特征。
- 人物数量、身份方向和服装方向。
- 独立物理场景清单。
- 必须出现的产品、道具和品牌信息。
- 故事节拍骨架。
- 每类资产的最低交付要求。

这不是完整故事板，也不直接生成视频。

蓝图用于确定第二阶段需要生产什么，避免一上来生成一大批无关图片。

## 3.2 人物资产流水线

每个人物建立一个 `Character Pack`，至少包括：

1. **身份方向**
   - 年龄段、地域/气质、角色功能。
   - 不可变面部特征。
   - 是否来自真实参考人物。

2. **概念候选**
   - 默认生成 4 个候选。
   - 用户只需选一个“作为人物母版”。
   - 未选候选不进入下游，也不重复占用故事板。

3. **身份连续性**
   - 脸部三视图：正面、侧面、3/4 角。
   - 全身三视图：正面、侧面、背面。
   - 身高比例、发型、肤色、显著特征锁定。

4. **造型版本**
   - 服装、配饰、头盔/眼镜/面罩等遮挡物独立成版本。
   - 一个角色可以有多个造型，但每个镜头必须绑定明确造型版本。

5. **镜头准备**
   - 只有故事镜头真正需要时才生成表情、动作姿态或特殊角度。
   - 不预生成没有镜头消费方的动作图，控制成本与数据量。

6. **人物锁定门禁**
   - 必需的脸部、全身和当前造型齐全。
   - 系统一致性检查无阻塞项。
   - 用户确认母版。

人物未锁定时，可以继续编辑蓝图，但不能进入依赖该人物的付费镜头生成。

### 无人物广告

若创作蓝图判断不需要人物：

- 人物区显示“本项目不需要人物”。
- 不出现空卡片、警告或待补齐提示。
- 不创建人物节点，也不要求用户跳过一个形式化步骤。

## 3.3 场景资产流水线

每个独立物理空间建立一个 `Scene Pack`，至少包括：

1. **空间身份**
   - 场景名称和用途。
   - 室内/室外、时间、天气、空间布局。
   - 材质、光线、固定建筑元素。

2. **场景母版候选**
   - 默认 4 个候选。
   - 先选定空间结构与氛围，不嵌入人物或产品。
   - 锁定后形成场景母版。

3. **可用机位**
   - 建立镜头：交代空间。
   - 反打位：保证对话或动作方向。
   - 交互位：人物或产品真正发生动作的位置。
   - 细节位：仅在故事确实需要时生成。

4. **场景约束**
   - 固定布局不得在不同镜头中漂移。
   - 时间、天气、光向、湿度等连续性字段有明确版本。
   - 场景中可移动的独立物体归道具；固定家具仍属于场景。

5. **镜头入景**
   - 故事与镜头阶段再把人物、产品和场景母版合成为关键帧。
   - 关键帧属于 `Shot`，不反向污染场景母版。

6. **场景锁定门禁**
   - 母版已选定。
   - 故事所需机位齐全。
   - 空间与光线连续性无阻塞项。

### 多场景项目

第二阶段顶部显示真实完成度：

```text
人物 1/1 已锁定    产品 1/1 已锁定    场景 2/3 已锁定
```

用户点击“场景 2/3”直接定位唯一缺失场景，不再显示大段解释。

## 3.4 产品与道具流水线

产品不能只保存一张主图。

最低资产包包括：

- 产品母版。
- 故事需要的多角度视图。
- Logo、型号、结构和材质等不可变特征。
- 关键细节局部。
- 可允许变化和绝对禁止变化的边界。

道具只为会参与动作或会影响连续性的独立物体建档。固定背景元素归场景，避免资产数量无意义膨胀。

## 3.5 资产候选与版本状态

所有人物、产品、场景、关键帧共用一套状态：

```text
draft → generating → candidates_ready → selected → locked
                   ↘ failed
locked → revised（产生新版本，不覆盖旧版本）
```

候选是同一版本内的选择；修订才产生新版本。两者不能混用。

普通用户只看到：

- 生成中
- 请选择一个
- 已锁定
- 需要处理

技术状态、供应商错误和模型参数只在详情或高级画布中出现。

场景卡只描述空间本身。带人物、产品和动作的画面进入镜头关键帧，不塞回场景卡。

## 五、故事与镜头如何消费资产

每个镜头必须显式绑定：

- 故事节拍。
- 人物版本与造型版本。
- 产品版本。
- 场景版本与机位。
- 道具版本。
- 上一镜头连续性约束。

镜头数据流：

```text
ShotSpec
  → KeyframeCandidate × N
  → 用户选择 Keyframe
  → VideoCandidate × N
  → 用户选择 Video
  → ReviewDecision
```

关键帧和视频都保留候选，但故事板只展示被选中的版本。

单镜重做只使以下内容失效：

- 当前镜头候选。
- 明确引用当前镜头末帧的后继镜头。

它不能导致无关人物、场景或整部作品重新生成。

## 六、自动关联画布

## 6.1 画布定位

画布是“生产血缘与排错视图”，不是另一套创作入口。

每个任务从创建开始就有一份可计算的图投影。用户执行以下动作时，系统自动更新：

- 上传或更换参考。
- 完成参考分析。
- 生成或锁定人物、产品、场景。
- 建立故事节拍和镜头。
- 生成候选、选择候选、创建新版本。
- 触发审核、重做或失效。

普通用户不需要拖节点或连线。

## 6.2 自动分组

画布只使用五种固定泳道：

```text
证据与目标 → 基础资产包 → 镜头关键帧 → 视频候选 → 审核与成片
```

组内再按业务实体聚合：

- 人物 C01 / 造型 A
- 产品 P01
- 场景 S01
- 镜头 SH01

默认只显示：

- 当前选中版本。
- 当前有效依赖。
- 阻塞或失败节点。

历史候选、已废弃版本和重试记录按需展开，防止生成历史铺满画布。

## 6.3 画布界面

```text
任务关系图 · 只读                                  [筛选] [历史版本]

状态：全部  类型：全部  仅看异常 □  仅看当前版本 ☑

┌─ 证据与目标 ─┐  ┌─ 基础资产包 ──────────────┐
│ 718.mp4       │→ │ P01 跑车 · 已锁定          │
│ 分析 v2       │  │ C01 赛车手 · 造型 A        │
└───────────────┘  │ S01 湿润山路 · 已锁定      │
                   └──────────┬──────────────────┘
                              ↓
                   ┌─ 镜头 SH04 ─────────────────┐
                   │ 关键帧 v3 · 已选中           │
                   │ 使用 C01/P01/S01             │
                   └──────────┬───────────────────┘
                              ↓
                   ┌─ 视频候选 ─┐ → ┌─ 审核 ─────┐
                   │ 1 ✓ 2 3    │   │ 连续性通过 │
                   └────────────┘   └────────────┘
```

节点侧栏显示：

- 业务名称和预览。
- 当前版本。
- 上游来源和下游影响范围。
- 生成时间、模型调用和费用记录。
- 错误详情和重试记录。

节点本身不塞满技术信息。

## 七、权限设计

画布入口只在任务中心或项目右上角向有权限用户显示。

建议权限：

- `story_ad.canvas.view`：查看关系图和节点详情。
- `story_ad.canvas.audit`：查看模型调用、费用、错误和重试记录。
- `story_ad.canvas.manage`：执行失效、重跑、切换版本等高级操作。

访问规则：

```text
允许访问 =
  super_admin
  OR (
    用户拥有对应 canvas 权限
    AND 用户本来就有该任务的访问权
  )
```

必须同时满足：

- 前端无权限时不渲染入口。
- 服务端无权限时返回 403。
- 图接口不向无权限用户返回任何节点、提示词、费用或模型信息。
- 直接输入 URL 也不能绕过。
- 权限分配、查看和高级操作写入审计日志。

普通用户甚至不需要知道画布存在。

## 八、低冗余的数据与代码方案

## 8.1 不建第二套生成系统

画布节点不是新的业务实体，不负责生成。

权威数据仍来自现有：

- 任务与修订。
- 参考分析。
- 人物、产品、场景和道具资产。
- 故事节拍与镜头。
- 生成任务、候选媒体和审核结果。

画布服务只做一件事：

```text
权威业务数据 → 标准化 Artifact/Edge 投影 → 画布 JSON
```

不复制媒体文件、不复制完整提示词、不复制任务状态。

## 8.2 不为每种资产复制一套表、接口和组件

底层采用统一 Artifact 契约：

```text
Artifact
  id
  task_id
  kind
  business_ref_type
  business_ref_id
  revision
  status
  selected_candidate_id
  source_fingerprint
```

统一边契约：

```text
ArtifactEdge
  from_artifact_id
  to_artifact_id
  relation
  active_revision
```

`kind` 可以覆盖：

- reference
- evidence
- character_concept
- character_identity
- character_look
- product_identity
- scene_identity
- scene_view
- story_beat
- shot_spec
- keyframe
- video
- review

这些是同一套契约的业务枚举，不是 13 套服务。

## 8.3 图数据优先按需投影

第一阶段不必持久化整张图。

推荐：

- 资产、镜头和生成记录仍由现有服务保存。
- `storyAdGraphProjectionService` 按任务读取现有实体并生成节点/边。
- 只额外保存管理员手工调整的节点位置、折叠状态和备注。
- 当数据量验证确实影响性能时，再增加可重建的图缓存。

这样不会出现“任务数据一套、画布数据又一套且二者漂移”。

## 8.4 前端只增加两个可复用层

1. `AssetCardRenderer`
   - 人物、产品、场景、道具共用卡片骨架。
   - 类型配置只提供字段和动作差异。

2. `StoryAdGraphView`
   - 权限通过后懒加载。
   - 普通剧情广告页面不打包或初始化画布运行时。

原有大文件只保留装配与兼容入口。新增功能前先迁出已有状态、保存和生成职责，确保核心旧文件净减少。

## 九、提示去重规则

普通用户界面只保留三类提示：

1. 唯一阻塞原因。
2. 唯一下一步动作。
3. 会付费、覆盖、删除或使下游失效的确认。

默认删除：

- 页面顶部整段流程说明。
- 同一状态在卡片、顶部、Toast、弹窗重复出现。
- 模型名、错误码、节点名和内部阶段名。
- “系统将自动……”类说明。
- 成功后没有下一步意义的 Toast。
- 没有对应动作的警告。

状态优先放在对象旁边：

```text
场景 S03 · 尚未选择母版                         [选择母版]
```

而不是：

```text
⚠ 为了保证后续内容生成质量，系统需要您先完成场景设置……
```

技术详情只出现在：

- 资产或镜头详情抽屉。
- 获授权的高级画布。
- 运维日志。

## 十、落地顺序

### P1：第二阶段资产契约与工作台

- 建立统一候选、选择、锁定、修订状态。
- 完成人物概念、脸部三视图、全身三视图和造型资产流。
- 完成场景母版、场景机位和连续性资产流。
- 产品建立主档、多角度和不可变特征。
- 第二阶段 UI 改为“唯一待处理项 + 资产卡片”。

验收重点：人物和场景必须真实产出可选资产，不能只保存描述文字。

### P2：故事与镜头显式绑定

- 镜头绑定人物/造型、产品、场景/机位和道具版本。
- 关键帧与视频候选分层。
- 单镜重做和依赖失效范围可计算。
- 故事板只显示被选中的图片与视频。

### P3：只读自动画布与权限

- 增加图投影服务。
- 增加 `view/audit/manage` 服务端权限。
- 超管和授权用户看到关系图入口。
- 默认当前版本、自动分组、仅异常筛选。

### P4：高级运维操作

- 节点级重跑、失效、切换版本。
- 费用和模型调用审计。
- 高风险操作二次确认和审计日志。

P4 不是 P1/P2 的前置条件，避免为了“做画布”拖慢真正的内容生成能力。

## 十一、验收指标

- 有人物项目的必需人物资产真实生成率：100%。
- 无人物项目误建人物资产：0。
- 每个场景有独立母版和所需机位，场景与镜头关键帧不混存。
- 镜头对人物、造型、产品、场景版本的绑定缺失：0。
- 修改单一资产导致无关镜头失效：0。
- 普通用户可见内部错误码、模型名和节点名：0。
- 同一状态在一个页面重复提示位置：不超过 1。
- 无权限用户的画布入口、接口数据和直链访问：全部拒绝。
- 普通页面未进入高级画布时，不加载画布运行时。
- 画布节点数量默认只包含当前有效版本；历史版本必须主动展开。
- 新增图能力不新增第二套生成 API、不复制媒体、不复制任务状态。

## 十二、已确认事实与仍属推断的边界

### 已确认

- 上述节点数、分组数、连线数和媒体类型来自当前可见页面。
- 人物全身母版、人物三视图、人物入景关键帧的候选数和提示内容来自所选节点界面。
- 场景分支确实同时连接了外部环境图、产品裁剪、关键帧和视频。
- 故事板确实把图片与视频分栏，并只呈现选用资产而不是全部底层节点。
- 不同竞品案例的图组织质量差异很大。

### 推断

- 竞品服务端如何持久化图、如何处理并发和版本锁没有从界面暴露。
- 竞品是否有完整的服务端权限、费用防重和任务隔离无法从只读页面确认。
- VIDO 的 ACL、图投影和统一 Artifact 契约是基于现有系统约束提出的设计，不是竞品实现复刻。

## 十三、最终决策

VIDO 不做“竞品画布复刻”，而做：

> 以资产生产为核心、以故事镜头为消费方、以自动关系图为后台投影的剧情广告系统。

普通用户获得更少提示、更明确的资产选择和更稳定的人物/场景连续性；超管与授权人员获得完整生产血缘和排错能力；代码只增加一套统一资产契约和一层图投影，不再建立第二套生成链路。

## 十四、全界面重构与迁移方案

### 14.1 重做什么、不重做什么

需要重做：

- 剧情广告页面外壳、导航和布局。
- 参考与目标、资产准备、故事与镜头、生成与审核四个工作区。
- 人物、产品、场景、镜头的卡片与详情抽屉。
- 页面状态管理、工作区切换和错误呈现方式。
- 仅对授权人员加载的关系图界面。

保留并复用：

- 任务、修订、自动保存和并发控制。
- 参考视频上传、分析和当前来源绑定。
- 现有人物、场景、剧情、镜头、生成和审核服务中已经正确的能力。
- 生成队列、费用记录、模型调用记录和生产部署链路。
- 本轮已完成的任务隔离、证据合并和付费前门禁。

结论是“前端体验整体重构”，不是“前后端全部重写”。

### 14.3 前端模块边界

```text
story-ad-v4/

├── api-adapter.js
├── workspaces/
│   ├── reference-workspace.js

```

约束：

- 一个权威 `task-store`，不再让 DOM、全局变量和任务 context 各保存一套状态。
- 一个 `api-adapter` 连接现有接口；工作区不能各自复制请求和 payload 组装。
- 人物、产品、场景、道具共用 `asset-card` 和候选选择器。
- `graph-view` 独立懒加载，不进入普通用户包。
- 旧 `new-story-ad-legacy-ui.js` 只保留旧入口和兼容转发，不再新增业务逻辑。

### 14.4 不采用一次性替换

采用并行路由和功能开关：

```text
旧界面：new-story-ad-v3
新界面：new-story-ad-v4
```

切换规则：

- 内部账号和指定测试任务先进入 V4。
- 普通生产用户继续使用 V3。
- 新旧界面读取同一权威任务数据，不复制数据库。
- 每完成一个工作区，先通过任务恢复、自动保存、刷新、并发和费用防重回归，再扩大范围。
- V4 达到完整验收门禁后才将新任务默认切到 V4。
- 历史任务兼容通过后，最后删除 V3 渲染和适配分支。

功能开关必须由服务端或权限配置控制，不能靠修改 URL 绕过。

### 14.5 六个实施阶段

#### R0：冻结契约与盘点旧界面

- 列出 V3 所有状态、接口、事件、自动保存和恢复入口。
- 给每个现有能力标记“保留、迁移、删除、暂缓”。
- 固定 V4 任务快照和资产契约。
- 建立旧核心 UI 文件行数与重复逻辑基线。

此阶段不改用户界面。

#### R1：新外壳与参考工作区

- 建立 V4 顶部栏、左侧导航、统一 store 和 API 适配层。
- 迁移参考上传、分析、来源绑定、任务隔离和错误门禁。
- 不增加新模型调用。

验收后，指定内部任务可以完整完成第一阶段。

#### R2：资产准备工作区

- 实现人物、产品、场景、道具统一卡片。
- 打通人物母版、脸部/全身三视图和造型版本。
- 打通场景母版、所需机位和场景锁定。
- 实现候选选择、锁定、新版本和失效范围。

这是整个重构的核心阶段，完成前不进入故事板重构。

#### R3：故事与镜头工作区

- 用已锁定资产生成节拍和镜头。
- 镜头显式绑定资产版本。
- 实现关键帧候选、连续性和单镜重做。
- 故事板只展示被选中的资产。

#### R4：生成与审核工作区

- 迁移视频生成、重试、费用确认和成片审核。
- 失败定位到具体镜头与资产。
- 全部模型调用继续经过现有服务端门禁。

#### R5：高级关系图与旧界面退役

- 增加只读图投影和服务端权限。
- 内部验证节点、版本、失效范围和费用审计。
- V4 全量门禁通过后逐步停用 V3。
- 删除旧渲染、重复状态和兼容分支，而不是永久保留两套代码。

### 14.6 代码体积门禁

每阶段必须满足：

- 不新增第二个同义 API。
- 不新增第二份任务状态。
- 新增工作区前先迁出旧文件中的对应职责。
- 旧核心文件行数必须净减少。
- 每个领域规则只允许一个服务端实现。
- 兼容层只能做字段转换，不能承载业务判断。
- V3/V4 双轨期结束时必须删除旧分支，不能长期双维护。

建议把“总代码行数不显著增长”改成可核对指标：

```text
新增 V4 业务代码
- 删除的 V3 重复代码
- 删除的重复提示、渲染、payload 和状态代码
= 可解释的净增量
```

关系图属于最后阶段，不得为了提前展示画布而复制资产或生成逻辑。

### 14.7 发布与回滚

- 所有 V4 工作区受功能开关控制。
- V4 只读取已有任务时可随时回到 V3。
- 一旦 V4 写入新版本资产，V3 必须能忽略不认识的扩展字段，不能覆盖或截断。
- 每次放量前核对活动任务为 0 或避开正在生成的任务。
- 出现任务串用、状态覆盖、重复付费或资产引用丢失时立即关闭 V4 开关。
- V3 删除前保留一个完整发布版本，可通过正常发布流程回滚，不在生产服务器手工改文件。

### 14.8 重构完成定义

不是“新页面能打开”，而是：

- 四个工作区均能从刷新、退出后重进和另一台电脑恢复。
- 人物和场景真实生成、选择和锁定，而不是只保存文字。
- 镜头消费明确资产版本。
- 单资产修改的下游影响范围正确。
- 普通用户提示数量符合去重规则。
- 无权限用户无法看见或调用关系图。
- 模型调用和费用防重回归通过。
- V3 对应逻辑已删除，仓库中不存在长期双实现。
