# 2026-08-13 剧情广告系统性整改总方案交接

> 文档性质：在 V251/V252 事实交接基础上形成的系统性整改实施方案  
> 目标分支：`codex/story-ad-v3-upgrade`  
> 当前生产：`20260813-ui-v251`  
> 当前 Git 基线：V251（按用户决定以生产运行制品为权威，V252 局部修改已可审计回退）
> 核心结论：**停止继续用版本号和单点补丁代替产品完成度；先重建权威数据、稳定身份、状态依赖、失败恢复和界面验收，再恢复真实生产全流程。**

## 0. 本文档解决什么

这份文件不是再列一次问题，也不是一份“以后优化”的建议清单。它是下一阶段开发、测试、迁移、发布和验收必须共同遵循的主方案，解决以下根本问题：

1. 已提供大量竞品、真实操作和参考材料，但没有转化成可执行产品合同。
2. V251 次版本迭代后，广告与剧情仍无法稳定从创建走到最终成片。
3. 人物、动物、商品、场景、剧情在跨步骤中发生覆盖、换 ID、失效、重复和无法复用。
4. 模型、供应商、网络失败与平台自身数据错误混在一起，导致定位和恢复困难。
5. 接口和局部测试通过，但真实页面刷新、返回、重进和后续步骤仍失败。
6. 用户被迫承担逐页找错和重复付费风险。
7. 继续叠加兼容分支可能增加代码复杂度并影响生产性能。

- 当日三方状态及问题事实：`docs/handoffs/2026-08-13-story-ad-v251-v252-home-continuation-handoff.md`

## 1. 不可改变的产品目标

### 1.1 唯一主流程

广告和剧情共用一条可理解、可恢复的生产主线，仅在业务字段和质量规则上分支：

```text
创建项目
→ 基础信息
→ 可选高级配置/参考材料
→ AI 识别建议
→ 用户确认人物/动物/商品/场景方案
→ 视觉资产
→ 正式剧情
→ 分镜
→ 镜头与关键帧
→ 视频/声音
→ 合成
→ 最终成片播放与下载
```

用户在任何页面都必须能回答四个问题：

1. 我现在在哪一步？
2. 这一步需要我做什么？
3. 哪些信息是我确认过且不会被系统擅自改变的？
4. 失败后保留了什么、重试什么、是否可能再次收费？

### 1.2 广告与剧情的明确边界

| 维度 | 广告 | 剧情 |
|---|---|---|
| 内容主体 | 必须有商品或服务主体 | 不强制创建商品主体 |
| 核心目标 | 商品证明、卖点表达、行动引导 | 人物目标、冲突、事件发展和结局 |
| 质量门禁 | 主体、卖点、证明镜头、品牌边界 | 人物、事件、因果、情绪和结局 |
| 参考材料 | 只能辅助识别，不能替换用户广告目标 | 只能辅助风格/结构，不能把故事改成广告 |
| 用户控制 | 内容类型必须由用户明确选择 | 内容类型必须由用户明确选择 |

AI 可以建议，但不得静默切换内容类型。

### 1.3 不再接受的完成定义

以下情况不能再写“已修复”“可以测试”或升级完整版本：

- 只通过函数或接口测试。
- 只验证当前失败按钮，未验证后续步骤。
- 通过人工改数据库才继续成功。
- 使用旧任务缓存、旧资产或演示数据假装新流程通过。
- 模型调用成功但业务产物不可用。
- 只在本地通过，生产没有发布后核对。
- 广告或剧情没有最终形成可播放视频。
- 页面刷新、返回和退出重进后状态不一致。

## 2. 竞品与参考材料如何真正进入研发体系

过去的问题不是竞品资料不足，而是资料没有形成强制合同。下一阶段必须建立四层可追踪关系：

```text
竞品/用户证据
→ 产品规则
→ 数据与界面合同
→ 自动化测试与生产验收证据
```

### 2.1 建立能力合同矩阵

每个竞品能力或用户要求必须形成一行合同，至少包含：

| 字段 | 含义 |
|---|---|
| `requirement_id` | 永久编号，不随页面改名变化 |
| 来源 | 用户反馈、竞品操作、截图或生产缺陷 |
| 用户目标 | 用户为什么需要它 |
| 页面位置 | 入口和结果出现在哪里 |
| 数据权威 | 谁能创建、覆盖、确认和失效 |
| 前置状态 | 什么条件下可操作 |
| 成功结果 | 用户可见的确定结果 |
| 失败恢复 | 保留、补齐、重试和费用规则 |
| 自动化用例 | 对应的 UI/API/服务测试编号 |
| 生产证据 | 任务 ID、版本、时间、结果 |

第一批必须覆盖：内容类型、参考材料显隐、AI 识别、人物/动物/商品/场景、方案确认、资产数口径、重规划、剧情、分镜、视频、声音、合成、失败恢复和费用确认。

### 2.2 建立两套黄金业务样例

黄金样例不是简单 mock，而是完整、稳定、可反复验证的产品合同。

#### 广告黄金样例

- 明确选择广告。
- 用户目标为红色电动跑车广告。
- 选择使用一条与花朵相关的参考视频，专门验证参考不得覆盖商品目标。
- 商品完整名和合理简称同时出现。
- 两个人物、一个商品、多个不同场景。
- 中途保存剧情、刷新、返回资产页、重新进入。
- 人为制造一个供应商失败和一个计费未知单元。
- 最终需要出现商品证明镜头、卖点、品牌边界与行动引导。

#### 剧情黄金样例

- 明确选择剧情。
- 选择不使用参考材料，验证高级配置入口隐藏。
- 两个人物、一只橘猫，验证动物不能进入普通道具。
- 存在人物简称/代词、多个场景、服装变化。
- 中途重规划一次，验证主体 ID、场景 ID 和已生成资产复用。
- 刷新、退出重进、部分失败恢复。
- 最终必须形成完整剧情、分镜、视频、声音和成片。

每套黄金样例要同时有：固定输入、预期权威数据、允许模型变化的范围、不可违反的语义条件、界面断言和最终媒体断言。

## 3. 目标数据架构：一个权威任务状态

### 3.1 单一权威原则

同一事实只能有一个权威来源。页面缓存、模型输出、参考分析和历史发布都不能成为平行真相。

| 数据 | 权威来源 | AI 权限 | 覆盖规则 |
|---|---|---|---|
| 内容类型 | 用户明确选择 | 仅建议 | AI 永远不能覆盖 |
| 项目名称 | 用户输入 | 可建议 | 只有用户保存才覆盖 |
| 内容目标 | 用户输入/用户确认的 AI 帮写 | 可生成草稿 | 参考材料不能直接覆盖 |
| 参考理解 | 参考分析结果 | 可生成 | 只作为证据，不直接成为目标 |
| 人物/动物/商品/场景方案 | 用户确认后的 Active Plan | 可提出新候选 | 新候选确认前不能替代 Active Plan |
| 视觉资产 | 已确认资产记录 | 可生成候选 | 替换需明确操作并保留历史 |
| 正式剧情 | 用户保存版本 | 可生成草稿 | 草稿不能覆盖正式版本 |
| 分镜及后续 | 对应阶段确认版本 | 可生成候选 | 按依赖图失效，不全局清空 |

### 3.2 任务聚合结构

逻辑上把一个项目视为一个 Task Aggregate，写入必须通过统一服务完成：

```json
{
  "task_id": "stable-task-id",
  "content_mode": "ad|story",
  "brief": {
    "value": "...",
    "authority": "user|user_confirmed_ai",
    "revision": 3
  },
  "reference_evidence": [],
  "active_plan_id": "plan-id",
  "entities": [],
  "scenes": [],
  "artifacts": [],
  "stage_revisions": {},
  "generation_units": [],
  "billing_reviews": []
}
```

这不是要求一次性更换数据库，而是要求所有服务遵守同一个业务模型，禁止路由、页面和模型回调分别修改互相重叠的 JSON。

### 3.3 所有写入带来源和并发条件

关键记录必须包含：

- `source_type`：user、reference、model、migration、recovery。
- `source_id`：对应输入、生成任务或历史资产。
- `created_at` / `updated_at`。
- `revision` 或乐观锁版本。
- `authority` 和 `confirmed_by_user`。
- `upstream_fingerprint`。

保存时使用期望 revision。若页面携带旧状态，返回明确冲突并刷新当前数据，不能默默覆盖新状态。

## 4. 稳定身份与重规划合并

### 4.1 双 ID 模型

每个人物、动物、商品和场景同时拥有：

- `entity_id` / `scene_id`：数据库永久 ID，创建后不变。
- `semantic_key`：用于识别重规划前后是否为同一业务对象。

模型返回的临时 ID 只能保存为 `provider_alias`，不能成为平台主键。

### 4.2 semantic_key 计算原则

- 人物：任务 + 角色身份 + 稳定关系/职责，不以服装或模型措辞为主键。
- 动物：任务 + 物种 + 剧情身份/归属关系。
- 商品：任务 + 商品/服务主体身份，不把颜色或材质单独当主体。
- 场景：任务 + 地点语义 + 叙事功能 + 时间段；镜头角度不是新场景。

算法必须确定性、可解释、可回归。模型可提供候选特征，但最终 key 不能依赖一次随机输出。

### 4.3 重规划 reconciliation

重规划不能直接 `replace all`，必须经过差异合并：

1. 精确 `entity_id` 匹配。
2. `semantic_key` 匹配。
3. 受控别名/简称证据匹配。
4. 无法确认时标记“待用户合并”，不得自动删除旧主体。

合并结果分为：`unchanged`、`updated`、`added`、`retired`、`needs_review`。

对已有资产：

- 主体未变、规格兼容：直接复用。
- 仅名称改变：复用并更新显示名。
- 服装/时代等视觉身份改变：保留旧资产，明确标记需要生成哪些视图。
- 主体移除：归档，不立即物理删除。
- 场景只改变镜头要求：复用场景资产，后续生成新镜头。

### 4.4 重规划验收条件

- 连续重规划 3 次，同一人物/动物/商品/场景永久 ID 不变。
- 页面刷新后仍使用当前权威 ID。
- 旧页面提交得到 revision 冲突，不覆盖新计划。
- 已完成资产不重复提交。
- 同语义场景不重复出现。
- 真正新增主体能独立创建并生成。

## 5. 修订依赖图与失效规则

### 5.1 依赖图

```text
content_mode ─┐
brief ────────┼→ plan → entity_assets ─┐
reference ────┘          scene_assets ─┼→ script → storyboard → shots → video/audio → compose
                                       └──────────────────────────────────────────────────────┘
```

每个阶段保存：

- 自身 revision。
- 上游 fingerprint。
- 状态：draft、ready、confirmed、stale、generating、partial、failed、completed。
- 失效原因和时间。

### 5.2 精确失效规则

| 修改动作 | 必须失效 | 不应失效 |
|---|---|---|
| 改内容类型 | 计划及全部下游 | 项目身份和历史版本 |
| 改用户目标 | 计划及依赖旧目标的下游 | 原始参考证据 |
| 增加参考材料 | 新的识别候选；用户确认后再影响计划 | 当前 Active Plan 不应立即消失 |
| 改人物显示名 | 需要重渲染的文本 | 已确认视觉资产和场景 |
| 改人物核心外观 | 该人物视觉资产及依赖镜头 | 其他人物和无关场景 |
| 改一个场景 | 该场景资产和相关镜头 | 其他场景、人物资产 |
| 保存正式剧情 | 分镜及其下游 | 人物/商品/场景计划与资产 |
| 改一个分镜 | 对应镜头、视频和合成 | 其他分镜和上游内容 |
| 改配音 | 音频与最终合成 | 画面资产和视频 |

### 5.3 Active Plan 规则

- 候选计划与 Active Plan 分开保存。
- AI 重规划只创建候选，不覆盖 Active Plan。
- 用户确认候选时才原子切换 Active Plan。
- 切换前展示新增、修改、归档、需重生成和可复用资产数量。
- 保存剧情只检查计划的上游 fingerprint，不使用无关的全局 revision 拒绝继续。

## 6. AI 调用治理

### 6.0 模型能力前提与本轮责任边界

本项目当前文本、图像、视频等模型类型已经齐备，用户核对的竞品也使用同类模型。因此整改不得再把大批次失败笼统归因为“模型能力不够”，更不能把换模型当作默认解决方案。

当前应优先按平台编排问题排查：

1. 模型路由是否选中了适合当前阶段、输入类型和审核边界的模型。
2. 提交前是否真正应用了已有模型审核规则和合规表达指南。
3. 提示词、参考图片、外部 URL、尺寸、格式和批次数量是否满足供应商契约。
4. 并发、限流、单候选超时和阶段总预算是否合理。
5. 供应商已受理、平台超时、审核拒绝、下载失败和平台代码异常是否被错误混成 HTTP 500。
6. 部分成功是否被保留，失败单元是否被错误升级成整个批次失败。
7. 回调、轮询和发布阶段是否存在旧 revision、旧 ID、幂等冲突或竞态。

只有在同一确定输入绕过平台编排、直接按供应商官方契约调用仍稳定失败，并且已经排除审核、限流、媒体可达性和参数问题后，才可以把失败归到模型/供应商能力边界。该结论必须附原始供应商错误分类、请求规格摘要和可重复证据，不能凭 HTTP 500 推断。

### 6.1 模型只返回候选，不直接写权威数据

调用链必须是：

```text
构造带版本的输入快照
→ 调用候选模型
→ 结构解析
→ 领域验证
→ 语义一致性验证
→ 生成候选 artifact
→ 用户确认或自动采用明确允许的低风险结果
→ 原子发布
```

任何模型回调不得绕过发布服务直接覆盖用户目标、Active Plan 或正式剧情。

### 6.2 候选与预算策略

- 每个候选有独立超时。
- 整个阶段有总预算。
- 超时、网络错误、限流、非法 JSON、字段缺失分别记录。
- 只有可恢复错误才切换候选。
- 领域验证失败保留原始结果摘要和规则编号，不能只写“模型失败”。
- 阶段耗尽后显示已尝试候选、失败原因和保留结果。

### 6.3 质量门禁

质量门禁分三层：

1. 结构层：字段、类型、长度和引用完整。
2. 领域层：广告/剧情规则、主体和场景关系。
3. 证据层：简称、别名、代词必须能追溯到权威主体，不能只靠颜色或普通词通过。

每条规则必须有正例、近似正例和反例。门禁失败时显示哪条规则不满足，并允许用户看到和修改候选，不把有效模型输出直接丢弃。

### 6.4 内容识别边界

- AI 识别结果显示为“建议”，与“用户已确认”视觉区分。
- 广告/剧情由用户选择，识别不得修改。
- 参考视频不得覆盖用户 brief。
- 人物、动物、商品和场景分类必须保留原始证据片段。
- 无法确认的分类进入待确认列表，不强行落入“道具”。

### 6.5 审核规则与合规表达前置

已有审核规则和合规表达指南必须成为生成编排的正式阶段，而不是散落在提示词里的说明文字。目标是合规、可解释地减少无效提交，不是规避供应商安全政策。

每个生成单元提交前执行：

```text
业务意图与主体识别
→ 文本/媒体风险分类
→ 合规规则匹配
→ 在不改变用户意图的前提下规范表达
→ 参数、尺寸、格式、URL 可达性预检
→ 展示重要改写或要求用户确认
→ 才提交供应商
```

硬性要求：

- 规则版本、命中编号、原始意图摘要、规范化结果和是否需要用户确认必须可审计。
- 规则只能处理表达方式和供应商输入要求，不能悄悄删除主体、改剧情或把广告改成其他内容。
- 明确禁止内容直接阻断并给出可理解原因，不通过同义改写绕过安全限制。
- 已经通过预检的相同输入使用规则版本和输入指纹缓存，不在批次内重复计算。
- 供应商仍审核拒绝时，将新证据回收到规则测试集，经人工确认后更新规则；不能即时自动放宽所有请求。
- 人物主图、服装细节、动物、商品、场景、视频和音频分别使用对应规则集，不能用一条通用提示处理全部媒体阶段。

### 6.6 批次编排、并发与熔断

大量主体/多视图不能一次无控制地并发提交。生成计划先拆为独立单元，再按供应商、模型、媒体类型和风险级别分队列：

- 每个供应商设置并发上限、每分钟速率和排队上限。
- 批次采用小窗口推进；先用一个代表单元验证路由、审核和媒体可达，再扩大并发。
- 同类错误在短窗口达到阈值时自动熔断该路由，停止后续提交，保留排队单元，避免“大批次一起失败”。
- 429/限流按 `Retry-After` 或指数退避重试；审核拒绝、参数错误和确定性业务错误不得盲目重试。
- 网络断开、供应商 5xx 和超时仅在费用状态明确、幂等键有效时自动重试；计费未知立即转人工门禁。
- 批次结果按单元统计成功、失败、待核对和未提交，单个单元失败不能把成功资产回滚。

### 6.7 HTTP 500 消除方案

HTTP 500 只能表示平台未预期代码异常。所有已知失败必须映射为稳定错误合同：

| 类型 | 建议 HTTP/业务状态 | 页面行为 |
|---|---|---|
| 用户输入或参数不符合契约 | 400 / `input_invalid` | 定位字段并允许修改 |
| 页面 revision 已过期 | 409 / `revision_conflict` | 只读保护并刷新当前状态 |
| 审核规则阻断 | 422 / `policy_blocked` | 显示规则类别和安全调整入口 |
| 模型结构或领域验证失败 | 422 / `candidate_invalid` | 保留候选摘要，可换候选/编辑 |
| 供应商限流 | 429 / `provider_rate_limited` | 排队并显示预计重试时间 |
| 外部媒体不可读取 | 422/424 / `media_unreachable` | 重新上传或改用 file ID |
| 供应商超时/不可用且费用明确 | 502/504 / `provider_unavailable` | 安全重试或切换候选 |
| 供应商提交状态不明 | 202/409 / `billing_review_required` | 禁止自动重提，人工核对 |
| 平台未预期异常 | 500 / `internal_error` | 支持编号、保留状态、服务端告警 |

实现要求：

- Provider Adapter 把不同供应商错误先归一化，路由层不得直接透传杂乱错误或统一包装成 500。
- 每个错误返回 `operation_id`、稳定 `error_code`、是否可重试、是否可能计费、保留结果和建议动作。
- 500 自动关联结构化日志和告警，记录最早异常边界；禁止只向用户显示“生成失败”。
- 前端不得把所有非 2xx 都显示为同一提示。
- 建立生产错误率指标：按阶段、供应商、模型、错误码和版本统计；大批次失败必须能在同一看板看出共同原因。
- 发布门禁加入“已知错误不得返回 500”合同测试，以及批次中单元失败不扩散测试。

### 6.8 模型路由验收

为每个阶段建立路由表：主模型、备用模型、支持输入、最大负载、审核规则集、超时、并发、费用级别和允许切换的错误类型。验收不比较“谁更强”，而验证：

- 相同输入经平台调用与供应商契约调用的结果分类一致。
- 审核前置后，大批次确定性拒绝在提交前被发现。
- 限流不会形成雪崩式重试。
- 单候选失败能够切换，阶段预算不会被首候选吃完。
- 已成功单元和供应商任务 ID 在超时后仍被找回。
- 所有预期外 500 都有回归用例，修复后转为明确业务错误或真正成功。

## 7. 媒体供应商、失败恢复与费用保护

### 7.1 生成单元模型

每张图、每段视频、每条音频都是一个独立 `generation_unit`：

```text
planned → submitted → provider_processing → succeeded
                                   ├→ failed_safe
                                   └→ billing_unknown
```

记录输入指纹、供应商任务 ID、尝试次数、费用状态、输出资产、错误分类和检查点。

### 7.2 幂等与检查点

- 幂等键必须包含任务、阶段、目标永久 ID、规格和输入指纹。
- 不同场景/人物不能共用键。
- 完全相同输入重复点击返回同一任务。
- 已成功单元不重复提交。
- 部分失败只补缺失单元。
- 输入变化生成新单元，旧单元保留审计关系。

### 7.3 计费未知硬门禁

- 供应商提交后响应不确定，标记 `billing_unknown`。
- 未经人工授权不得自动重提。
- 页面列出目标、供应商、提交时间、是否有任务 ID、可能费用和已有产物。
- 授权编号必须稳定，刷新和状态变化不能漂移。
- 发布、重启和恢复任务不得绕开该门禁。

### 7.4 媒体交付

- 外部 URL 进入供应商前做短超时匿名探测。
- 记录 Content-Type、Content-Length、Range、首字节和完整下载时间。
- 优先上传到供应商文件接口或稳定对象存储，复用 `file_id`。
- 探测结果缓存，不阻塞普通页面首屏。
- 本地裁剪/派生只用于不会改变主体语义的安全场景，并记录来源资产。

## 8. 界面与交互重新收敛

### 8.1 第一步信息架构

```text
左侧：基础信息与成片设置
  1. 项目名称
  2. 内容类型（必选：广告/剧情）
  3. 内容目标/剧情需求
  4. 时长、比例、清晰度等成片设置

右侧：高级配置
  1. 是否使用参考材料
  2. 选择“是”后展开参考视频、商品/服务主体参考
  3. AI 识别建议与待确认项
```

选择“否”时，参考上传区域必须从布局和键盘焦点中同时隐藏；选择“是”才加载相关控件。

### 8.2 提示放置规则

- 字段约束放字段下方。
- 当前操作错误放操作区域内。
- 全局连接或版本错误放页面顶部。
- 费用风险必须紧邻确认按钮。
- 不把上一步错误放到下一步页面。
- 错误包含：发生了什么、保留了什么、下一步能做什么。

### 8.3 统计口径

禁止一个数字同时代表主体和文件。统一显示：

```text
主体：人物 2｜动物 1｜商品 1
场景：已规划 5｜已确认 4｜已生成 2
资产文件：成功 13｜失败 1｜待确认 2
生成任务：运行中 0｜计费待核对 1
```

所有列表、侧栏和详情页使用同一个统计服务结果，不能各自计算。

### 8.4 状态一致性

每个关键操作必须验证：

- 当前页面立即显示正确结果。
- 强制刷新后相同。
- 返回上一步再进入相同。
- 退出项目再打开相同。
- 另一浏览器窗口打开时能识别 revision 冲突。
- 旧页面收到新版提示后只读保护，不允许继续写入。
- 中文名称、提示、模型返回和下载文件名无乱码。

- 禁止路由直接修改多个状态文件。
- 禁止前端从名称猜当前主体 ID。

- 禁止页面加载触发模型调用或全库扫描。

- 禁止为了通过测试放宽业务门禁或伪造成功状态。

每次新服务接管一条路径时必须同时登记：

- 替代了哪个旧函数/分支。
- 哪些兼容读取临时保留。
- 删除旧路径的版本和条件。
- 代码行数、重复分支和依赖变化。

不得长期保持“旧逻辑、新逻辑、修复兜底”三套并行。

## 10. 数据迁移方案

### 10.1 先只读审计

先实现 `taskStateAuditService`，对生产任务只读输出：

- 权威内容类型和 brief 来源。
- 当前/候选计划及 fingerprint。
- 主体与场景永久 ID、semantic_key、别名。
- 重复主体/场景。
- 孤立资产和可复用资产。
- 各阶段 revision 与错误失效原因。
- 活动、失败和计费未知生成单元。

审计器不进入普通请求，不调用模型，不修改数据。

### 10.2 影子字段

第一阶段只新增可空字段和索引：

- `semantic_key`
- `authority`
- `upstream_fingerprint`
- `stage_revision`
- `generation_input_hash`

旧读写路径继续运行；后台分页生成影子值并比较，不改变用户结果。

### 10.3 分批回填

顺序：

1. 最近活跃且无运行任务的项目。
2. 当日广告/剧情验收任务。
3. 历史已完成项目。
4. 历史失败和计费未知项目只审计，不自动重提。

每批前备份，限制行数和时间，记录冲突；无法自动合并的对象进入人工核对，不强制覆盖。

### 10.4 读写切换

```text
旧写 + 影子计算/比较
→ 新旧双读只比较（单一旧写）
→ 新写 + 旧兼容读
→ 新读新写
→ 删除旧写和临时兼容
```

禁止真正的双写权威数据，避免两套状态漂移。

## 11. 测试体系

### 11.1 测试层级

| 层级 | 目标 | 必须覆盖 |
|---|---|---|
| 纯领域测试 | 权威、身份、合并、失效规则 | 正例、反例、边界、最大长度 |
| 服务集成测试 | 写入、并发、检查点、计费 | SQLite/文件持久化、失败恢复 |
| API 合同测试 | 请求响应和冲突 | revision、错误码、只读状态 |
| 浏览器 UI 测试 | 用户真实操作 | 显隐、刷新、返回、重进、乱码 |
| 供应商沙箱/桩 | 超时和异常矩阵 | 限流、非法结构、下载失败、未知计费 |
| 生产只读审计 | 真实状态 | 文件、数据库、任务、费用 |
| 生产黄金冒烟 | 最终证明 | 广告/剧情各一条完整新任务 |

### 11.2 必须新增的回归矩阵

- 同一主体完整名、简称、别名、代词和无关同色词。
- 猫/狗等有生命主体与普通道具区分。
- 同场景不同镜头、不同场景相同时间、名称变化但语义相同。
- 连续重规划、并发重规划、旧页面提交。
- 部分成功、部分失败、超时后供应商实际成功、计费未知。
- 保存剧情后计划不失效；修改人物外观只失效相关资产。
- 内容类型广告/剧情不能被 AI 或参考切换。
- 选择参考材料是/否的界面和数据行为。
- 中文、空格、特殊符号、超长名称和最大主体/场景数量。
- 页面强刷、退出重进、服务重启、发布切换。

### 11.3 真实 UI 完整验收

广告和剧情必须分别使用全新生产任务，按用户可见页面完成每一步。每一步记录：

- 页面和操作。
- 输入快照。
- 用户可见结果截图。
- 权威状态只读核对。
- 模型/媒体调用数量。
- 费用状态。
- 刷新与重进结果。
- 失败恢复过程。

最终验收必须实际播放输出视频，并核对人物、商品、场景、剧情、声音和字幕一致性。接口成功不能替代播放验收。

### 11.4 防止测试自身失真

- UI 测试不得直接调用内部服务替代按钮。
- 不允许跳过必填步骤写数据库。
- mock 只用于异常矩阵，黄金验收使用真实页面与真实持久化。
- 每个测试任务带唯一前缀，不复用旧任务结果。
- 测试记录区分“执行”“跳过”“阻塞”，不能把计划写成已通过。

## 12. 性能与代码体积门禁

整改目标应减少重复生成和重复计算，不能让普通用户请求承担审计与迁移成本。

### 12.1 热路径约束

- `semantic_key` 在写入/重规划时计算，读取直接查索引。
- revision 和 fingerprint 在保存时更新。
- 审计器只按需运行，不接入普通页面。
- 列表统计使用统一聚合查询，不逐任务 N+1 扫描。
- 媒体探测异步、短超时、可缓存。
- UI 测试代码不进入生产包。
- 历史回填分页、限速、可暂停。

### 12.2 发布前基线

每阶段记录修改前后：

- 项目列表、项目详情、方案详情、资产列表 API 的 p50/p95。
- 单请求 SQL 数量和最慢查询。
- 页面首屏请求数、JS/CSS 体积和可交互时间。
- PM2 RSS/heap、事件循环 p95、CPU。
- 重规划耗时、模型调用数、重复生成单元数。

建议门禁：在同等数据规模下，核心只读接口 p95 不得无解释退化超过 10%；首屏静态资源不得因本次领域重构明显增大；不得出现持续内存增长或同步全表扫描。若确需牺牲少量延迟换一致性，必须在交接中量化并由用户确认。

### 12.3 预期收益

- 稳定 ID 减少重复资产生成。
- 精确失效减少无关步骤重跑。
- 检查点和幂等减少重复费用。
- 统一统计和 view model 减少前端重复请求。
- 删除旧分支降低维护和执行复杂度。

## 13. 可观测性与问题证据

每个用户操作生成统一 `operation_id`，贯穿浏览器请求、API、领域服务、模型调用、供应商任务和持久化事件。日志必须能回答：

- 谁在何时修改了哪条权威数据？
- 修改前后 revision 和 fingerprint 是什么？
- 哪个主体/场景永久 ID 被使用？
- 模型返回为何被接受或拒绝？
- 哪些单元提交给供应商，费用状态是什么？
- 页面为什么显示当前阶段和数量？

日志禁止记录密码、Token、API Key、私钥和完整敏感素材。用户错误提示使用支持编号关联服务端证据，不泄露内部信息。

管理审计页至少提供：任务状态快照、依赖图、重复/孤立数据、运行任务、计费未知和最近错误；默认只读。

- 统一 generation unit。

- 稳定媒体上传/文件 ID 复用。

退出条件：异常矩阵全部可解释恢复；所有已知失败均返回稳定业务错误而不是 500；同类错误触发熔断而非扩大批次失败；未知费用不自动重提；成功单元不重复生成。

交付：

- 统一第一步信息架构和高级配置。

- 错误、保留结果、下一步和费用提示归位。

退出条件：广告/剧情 UI 自动化覆盖显隐、刷新、返回、重进、并发冲突和中文显示。

交付：

- 剧情、分镜、镜头、关键帧、视频、声音、合成逐阶段合同。

- 最终视频播放、下载与状态读回。

退出条件：本地/预发布两套黄金样例从创建到播放完整通过，无人工改数据。

### 阶段 7：生产发布与真实验收

交付：

- 不可变 release、备份、原子切换和回滚点。
- 发布后文件清单、PM2、内外网、SQLite、活动任务核对。
- 广告、剧情各一条全新真实生产任务完整记录。

退出条件：两条任务均形成可播放成片；刷新重进一致；无乱码；无已知阻塞；费用和调用数可核对。

| 模板 | 共享内核之外的必验项 |

### 与当前代码的根因对齐

1. `assetPlanPublicationService.publish()` 为每次候选方案生成新的随机 `candidateId`；`sceneAssetService.mergeSceneAssets()` 又主要依赖 `scene_id` 精确相等合并。重规划换 ID 时，已有资产无法天然复用，这是 DATA-005 的代码根因链。
