## 二、今天的目标与用户决策

今天完成的最终目标不是为某个展厅写死一套页面，而是把人物、场景、机位、场景衔接和空间能力升级为通用生产合同：

1. 场景必须适配所有行业和用户诉求，不能预设家庭、室内、室外或固定蒙太奇结构。
2. 多人物、多场景以及人物在哪个场景出场，需要一次规划并可人工修改。
3. 同一场景内的区域/机位切换与真正的跨场景转场必须分开表达；只有 `scene_id` 改变才建立跨场景衔接。
4. 普通多视角图片、360全景和完整空间模型必须按真实素材能力区分，不允许用网格或五张普通图片冒充贝壳/Realsee式3D漫游。
5. 重生成人物视觉档案不能无条件推翻蓝图、文字故事板、场景和人物分配；人物身份/角色语义变化与服饰、鞋履、饰品、外观图片变化必须分开处理。
6. 旧代码必须停止执行；用户刷新后必须获取新构建，缓存中的旧客户端也不能继续写入新数据。
7. 既有年龄、人物服装、鞋履、饰品、档案和图片切换优化不得被本轮场景升级覆盖。

## 三、修改前后的关键数据流

### 3.1 人物完整档案重生成

修改前：

`重生成人物完整档案 → 人物版本变化 → 蓝图、故事板、关键帧、视频等大范围失效 → 人物场景关系可能重新变成待分配`

修改后：

`确认重生成人物视觉档案 → 保持稳定人物 ID → 保留人物身份、蓝图、文字故事板、场景、语音和人物分配 → 只失效线稿/关键帧/视频等视觉下游 → 新人物视觉版本继续绑定原场景`

只有身份、角色、年龄、动作能力等语义发生实质变化时，才进入语义变更流程并重新复核剧情结构。单纯更新服饰、鞋履、饰品、表情、动作图或人物档案图片不会重做整个任务。

### 3.2 人物与场景分配

修改前：

`只读取当前 storyboard_table → 当前故事板为空 → 人物卡显示“待分配”`，即使历史已发布故事板仍有有效绑定也无法恢复。

修改后：

`人工保存分配 > 当前文字故事板 > 与当前人物/场景兼容的历史已发布故事板 > 单人物单场景建议 > 待确认`

保存时使用 `assignment_revision` 乐观并发门禁，过期页面写入返回 409，避免两页互相覆盖。

### 3.3 通用场景世界

修改前：

`场景图片/布局 → 固定网格代理 → 无法看到真实场景图片，普通多视角图也容易被误解为360/3D`

修改后：

`用户需求 + 场景资产 + 空间数据 → SceneWorld v2 → 多视角照片 / 360观察点 / 空间模型分级能力 → 观察点、机位、人物站位、行动路径与跨场景入口按真实能力启用`

当前“光影艺廊”只有普通多视角图片，因此权威模式是 `photo_views`；`supports_panorama=false`、`supports_spatial_model=false`。要达到贝壳/Realsee式效果，需要至少补充2:1全景观察点；完整3D还需要多观察点、深度/几何数据和观察点连接路线。

### 3.4 新旧前端版本

修改前：

`浏览器缓存旧 HTML/JS → 继续加载旧模块 → 旧写请求可能覆盖新版状态`

修改后：

`/story-ad/ JS/CSS no-store → 统一 build ID → 旧脚本地址 410 → 旧 build 的写请求 426 → 用户刷新后重新获取完整新版模块`

当前构建：`20260803-scene-world-regeneration-v4`；场景合同：`scene-world-v2`。

## 十、回家后建议继续优化的顺序

1. **先确认拉取与本地回归**：核对最终远端 HEAD、运行 `npm run platform:upgrade:test`、启动 3007。
2. **完善真实空间数据入口**：为每个场景增加全景上传/生成、观察点管理、热点连接和数据质量门禁；不能继续只扩展网格代理。
3. **实现真正的360查看器**：消费2:1等距柱状全景，支持拖动环视、观察点切换、视角方向与机位联动。
4. **规划3D重建接入**：明确真实扫描、多视角重建或第三方空间服务的供应商与成本；在有深度/几何数据后再启用完整3D漫游。
5. **加强场景生成前编辑**：把场景内容、区域、材质、光线、人物动作、观察点和衔接要求放在生成确认前，支持只补生成当前场景缺失能力。
6. **完善多场景衔接编辑器**：资产中心编辑宏观路线，分镜台编辑相邻镜头的起止状态、视觉锚点、运动方向、声音桥和转场方式。
7. **处理当前任务审核内容后再做真实生成验收**：先消除 `PROVIDER_CONTENT_AUDIT` 风险，再执行一次受控、可计费的端到端生成；执行前再次确认不会重复扣费或覆盖现有资产。
